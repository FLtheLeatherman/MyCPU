## 架构设计

这是一个基于 **RISC-V 指令集**（RV32I 子集）的 **五级流水线（5-Stage Pipeline）** CPU。其设计特点在于利用 Assassyn 框架的模块化特性，通过异步调用（`async_call`）传递数据流，并结合全局信号处理冒险与控制。

### 1. 架构核心：基于 DAG 的拓扑执行流

整个 CPU 的运行逻辑不再是简单的线性流水线，而是一个分层的 DAG。每个周期，仿真器按照拓扑序依次执行节点。

#### 核心拓扑图例 (Control & Data Path DAG)

```text
[层级 1: 状态提供与初步解码 (Upstream)]
+-----------+    +---------+    +---------+    +---------+    +---------+
|  Fetcher  |    | Decoder |    |   EX    |    |   MA    |    |   WB    |
|(PC Regs)  |    |(Inst Reg)|   |(ALU Res)|   |(Mem Res)|   |(WB Data)|
+-----+-----+    +----+----+    +----+----+    +----+----+    +----+----+
      |               |              |              |              |
      | (PC)          | (rs1/rs2     | (rd_addr)    | (rd_addr)    | (rd_addr)
      |               |  addr)       |              |              |
      |               v              v              v              v
      |          +-------------------------------------------------------+
      |          |               Bypass Module (仲裁核心)                 |
      |          |-------------------------------------------------------|
      |          | 逻辑: 比较 rs_addr 与 ex/mem/wb 的 rd_addr             |
      |          | 输出: rs1_type, rs2_type, is_stall                    |
      |          +--------------------------+----------------------------+
      |                                     |
      |                                     | (Forwarding Types / Stall Signal)
      v                                     v
[层级 2: 执行逻辑 (Downstream)]      +-------------------------+
+----------------------+             |      DecoderImpl        |
|     FetcherImpl      |<------------|-------------------------|
|----------------------|  (Stall?)   | 逻辑: 根据 Bypass 类型   |
| 逻辑: 计算 NextPC     |             | 选择(Select)真实操作数   |
|      处理 Stall      |             | 组装 Ctrl 信号传给 EX    |
+----------------------+             +-------------------------+
```

**架构解读：**
1.  **上游 (Upstream)**：`Fetcher`, `Decoder`, `EX`, `MA`, `WB` 是状态的持有者（Pipeline Registers）。在每个周期的开始，它们向外暴露当前的内部状态（如指令中的寄存器索引、流水线寄存器中的目标地址）。
2.  **中游 (Arbitration)**：`Bypass` 模块作为汇聚点，收集了所有阶段的“生产信息”（EX/MA/WB 的目标寄存器）和“消费需求”（Decoder 的源寄存器）。它纯粹由组合逻辑构成，计算出当前时刻必须的数据流向。
3.  **下游 (Downstream)**：
    *   `DecoderImpl`：处于 DAG 的末端。它利用 `Bypass` 算出的“转发策略”，从 EX/MA/WB 的数据端口直接抓取最新的数据，实现了 **0 周期延迟的旁路**。
    *   `FetcherImpl`：接收 `Bypass` 计算出的 `is_stall` 信号，决定是否冻结 PC。

#### 内存子系统拓扑图例 (Memory DAG)

内存系统利用同样的机制解决了 IF 和 MA 对单端口 SRAM 的竞争，并处理了 Store 的时序要求。

```text
[层级 1: 访存请求源 (Upstream)]
+--------------+                +--------------+
|   Fetcher    |                |      MA      |
| (Curr PC)    |                | (ALU Result, |
|              |                |  Store Val)  |
+-------+------+                +-------+------+
        |                               |
        | (IF Addr)                     | (Data Addr, WData, We)
        |                               |
        v                               v
+-------------------------------------------------------+
|              MemoryUser (内存仲裁与控制器)              |
|-------------------------------------------------------|
| 逻辑:                                                 |
| 1. 优先级仲裁: EX/MA 读写请求 > IF 取指请求             |
| 2. Store Buffer: 锁存本周期的 Store 数据 (Delay Write)|
| 3. Mask Gen: 生成 Byte/Half Word 的写入掩码            |
+---------------------------+---------------------------+
                            |
                            v
                    +---------------+
                    |     SRAM      |
                    +---------------+
```

**架构解读：**
*   `Fetcher` 和 `MA` 是内存访问的**发起者**。
*   `MemoryUser` 是**仲裁者**。它位于 DAG 的下游，能够同时看到 IF 和 MA 的请求。
    *   如果 MA 阶段有 Load/Store，`MemoryUser` 会切断 IF 的访问路径（通常配合 IF 的 Stall）。
    *   它维护内部的 `RegArray` 来实现 Store 的跨周期写入（因为 SRAM 的写入通常需要在时钟边沿生效，或者为了模拟总线行为），对外表现为组合逻辑的地址路由。

### 2. 模块化功能总结

基于上述拓扑图，各模块的职责定义如下：

#### A. 状态维持层 (Upstream Roots)
这些模块主要负责**寄存器行为**（时序逻辑）和初步的**信号解包**。
*   **Fetcher**: 仅维护 `PC` 和 `Last_PC` 寄存器。
*   **Decoder**: 仅从 I-Cache/Input 拿到指令，拆解出 `rs1`, `rs2` 的索引（Index），供 Bypass 使用。
*   **EX / MA / WB**: 维护各自阶段流水线寄存器中的 `rd`（目标地址）和数据产出，供 Bypass 比较。

#### B. 核心仲裁层 (Mid-stream Logic)
*   **Bypass Module**: 全局的大脑。它不存储状态，只负责逻辑判断。它构建了从后（WB）往前（ID）的数据“虫洞”，使得 `DecoderImpl` 能在当前周期“看见”未来的结果。
*   **Memory User**: 内存的大脑。它屏蔽了底层 SRAM 的物理限制（单端口），向 `Fetcher` 和 `MA` 提供虚拟的独立访问接口，并处理复杂的写入对齐逻辑。

#### C. 逻辑执行层 (Downstream Leaves)
这些模块根据仲裁结果执行实际的 CPU 逻辑。
*   **DecoderImpl**: 真正的解码执行者。
    *   **输入**: 原始指令字段 + **Bypass 模块的决策** + 各阶段的旁路数据。
    *   **动作**: `real_rs1 = bypass_type.select(reg_val, ex_val, mem_val, wb_val)`。
*   **FetcherImpl**: 真正的取指执行者。
    *   **输入**: **Bypass 模块的 Stall 信号** + EX 阶段的 Branch Target。
    *   **动作**: 决定 `Next PC` 是 `PC+4`，还是保持不变（Stall），还是跳转（Branch）。

### 3. 设计亮点总结

1.  **拓扑序消解冒险**: 利用 Assassyn 的计算图特性，将“冒险检测（Bypass）”置于“数据读取（DecoderImpl）”的上游。这意味着在 DecoderImpl 真正打包数据传给 EX 之前，冒险就已经被解决，数据已经被替换为最新值。
2.  **解耦的控制流**: 传统的 CPU 设计中，Stall 逻辑往往散落在各个阶段。在本设计中，`Bypass` 模块集中处理了所有的 Stall 条件（如 Load-Use, Store 冲突），并分发给下游，逻辑非常清晰。
3.  **虚拟化内存端口**: `MemoryUser` 将物理的 SRAM 抽象化，使得 IF 和 MA 阶段写代码时仿佛拥有独立的内存，由拓扑序靠后的 `MemoryUser` 统一处理冲突。

### 4. 额外机制

#### 分支预测与冲刷
*   **策略**：Static Not Taken (默认不跳转)。
*   **修正**：利用全局寄存器 `branch_target_reg`。
    *   当 `branch_target_reg != 0` 时，IF 阶段将其作为 Next PC，ID 阶段将当前指令置为 Bubble (NOP)。
    *   MA 阶段可以看到此寄存器作用（虽然主要逻辑在 EX 和 IF）。

这套架构利用软件仿真器的特性，优雅地解决了硬件描述中复杂的连线问题，是一个非常规但高效的 RISC-V 实现方案。
